Distributed Transaction Orchestration (Saga Pattern)

Unlike a Monolith which commits in a single database transaction, Microservices coordinate across autonomous databases via network RPCs:

Step 1 Client Request POST /api/orders/checkout API Gateway (:8000)
→
Step 2 Inventory Reserve PUT /products/:id/stock Product-Svc (:8001)
→
Step 3 Authorize Payment POST /payments/charge Payment-Svc (:8004)
→
Step 4 Commit Local Order Insert order into orders.db Order-Svc (:8003)

Microservices Advantages

Strengths of decoupled service architecture:

  • Independent Scalability: Scale high-load services (e.g. Product Catalog) without duplicating payments.
  • Fault Isolation: A crash or memory leak in the Payment Service does not bring down Catalog browsing.
  • Polyglot Freedom: Services can use different languages, frameworks, and storage engines per domain.
  • Autonomous Deployments: Small teams can ship changes to User Service without coordinating a monolith release.

Microservices Complexities

Trade-offs and architectural costs to manage:

  • Network Latency: Inter-service HTTP hops introduce latency overhead compared to in-memory calls.
  • Eventual Consistency: Cannot use simple atomic SQL transactions; requires compensating transactions (Sagas).
  • Operational Overhead: Requires API gateways, service discovery, distributed tracing, and multi-container orchestration.
  • Debugging Difficulty: Tracing bugs across multiple services requires unified correlation IDs.
